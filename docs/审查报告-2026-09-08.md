## B. 项目不足之处（诚实清单）

现在能看清的短板，按"面试被问到会不会心虚"排序：

1. **没有真实生产流量**。单机、单用户、无鉴权、无并发设计，SQLite + Chroma 都是 demo 级存储。面试官问"上线过吗 / QPS 多少"只能答"可一键切换生产组件"——这是学生项目的天花板，承认比掩饰好。
2. **评测既当运动员又当裁判**。引用有效率、audit 判定都由 LLM 自己打分，10-20 题的评测集统计意义有限。需要抽样人工标注校准，否则五指标是"自嗨指标"。
3. **Tavily 是检索质量的上限**。1000 credits/月只够 30-80 次全链路演示；且 Tavily 对中文长尾信源覆盖一般，行业深度研究的"深度"会被搜索源限死。
4. **Auditor 本身也是幻觉源**。引用审计用 LLM 判断"证据是否支撑"，审计者自己会误判（尤其 flash 初筛档）。目前只有"flash 初筛 + 强模型复核"缓解，无法承诺 100%。
5. **模型路由的质量-成本权衡没有答案**。切到 Ollama 小模型省 token 但引入质量折损，折损多大没有量化——只能靠 P7 评测集回填，P4 上线路由时是"盲切"。
6. **Windows 开发环境与"生产感"的落差**。docker-compose 里的 Postgres/Milvus 只是"躺着"，没真正跑过；简历写"可切换"但没切过，深挖会露怯。
7. **图表是钩子不是功能**。requires_chart 只是个 TODO 占位（模板也半成品），P7 的 pyecharts 属于锦上添花，砍掉不影响主线——但文档里它出现在 P7 清单，容易被误判为承诺项。
8. **前端 5 天是双刃剑**。React 工作台对校招生是差异化，但做得糙（布局乱、无 loading 态、SSE 断线不重连）反而暴露工程审美不足。

## C. 我的观点与发展方向

### 观点

1. **这个项目的核心资产不是 9 个模块，是"每一层都有可量化的失败兜底"**。简历和面试的叙事单位应该是"我发现 X 会失败 → 用 Y 兜底 → 评测显示 Z"，而不是功能罗列。建议 P2 跑通起就在 `docs/cases/` 记录每个真实失败案例（死循环、引用造假被抓住、熔断触发），面试讲案例比讲架构值钱十倍。
2. **"没预算"是选题优势不是劣势**。成本感知调度、查询缓存、分层模型路由，这些在有钱团队里是"优化项"，在零预算项目里是"生存项"——被迫做深。建议把**"每份报告的 token 成本"提为评测五指标之首**，主打"穷人版 DeepResearch 的成本工程"定位。
3. **先窄后宽**。当前 9 个模块已经到了复杂度红线（约 20 天），再往上加特性必然烂尾。P6 求职版本之后的扩展全部走"可选插件"路线，不动核心链路。

### 后续发展方向（P6 之后按优先级）

1. **MCP 化（强烈推荐，工程量小话题性强）**：把 Attest 调研能力封装成 MCP server，接入任意支持 MCP 的客户端——2026 年 MCP 已是 Agent 交互事实标准，"我的调研 Agent 是一个 MCP 工具"这句话本身就是亮点。
2. **垂直信源 Scout**：ArXiv / GitHub trending / RSS（公众号、博客）专用检索器。行业深度研究的专业性来自垂直信源，而非通用搜索——也是缓解 B-3 的正解。
3. **增量重调研**：同一问题二次提问时 diff 式更新（只补新证据、复用旧引用编号），token 省 60%+，体验接近"订阅"。
4. **定时追踪报告**：cron 驱动"每周追踪某赛道并发简报"，把一次性工具变成持续性服务——这与定时自动化天然契合，也是产品完整度的加分项。
5. **远期**：用评测流水线积累的标注数据蒸馏本地小模型做 judge 初筛，把"audit 烧 token"的成本再压一档。
