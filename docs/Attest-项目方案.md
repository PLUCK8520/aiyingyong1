## 1. 项目定位

多 Agent 深度调研系统：自然语言提问 → **意图分流 → 规划（人工可确认）→ 双源混合检索 → 证据判别（含矛盾检测）→ 反思补检 → 撰写 → 引用忠实性审计** → 可溯源结构化报告。
全程 Token 预算治理 + 全链路 Trace，报告成果自动沉淀回知识库形成研究闭环。

- 技术栈：Python 3.13 + LangGraph；Qwen3（百炼免费额度）+ Ollama 本地
- 定位：求职作品集，每个新增模块都对应一个面试深挖点（见 §3）
- **叙事主轴（v2.2 调整）**：不以"模块清单"为主线，而以**三张可量化表**为主线——**成本表**（每份报告 token / ¥）、**质量表**（引用有效率 + 人工标注校准子集）、**失败案例表**（`docs/cases/`）。§3 的 9 个模块只是支撑这三张表的手段，不是目的；简历与答辩叙事单位建议为"我发现 X 会失败 → 用 Y 兜底 → 评测显示 Z"。

## 2. 总体架构

```
用户提问
 └─ Intent Router 意图路由
     ├─ direct → Direct Responder（秒回）
     └─ research → Planner（目标/子问题/大纲 JSON）
          └─ ★ 人工确认大纲（LangGraph interrupt/resume，可跳过）
               ├─ Web Scout（Tavily + 正文抓取）      ┐ Send API 按子问题
               ├─ Local Scout（BM25+向量 RRF + Rerank）┘ 动态扇出并行
               ├─ Evidence Judge：置信度 + missing_gaps + ★矛盾检测
               ├─ Reflect：不充分 → 补检循环（≤2 轮 + 预算熔断）
               ├─ Analyst：按大纲成文（含"争议与分歧"章节）
               └─ ★ Citation Auditor：逐句核验引用真实性（反幻觉）
                    └─ 结构化报告：摘要→分析→争议分歧→参考资料
                        [WEB1-1-1]/[LOC1-1-1] 统一引用编号（{类型}{轮次}-{子问题}-{序号}）
 └─ ★ 报告成果沉淀 → 向量库 research_memory（跨调研复用）
横切层：Thread 检查点 · 用户画像 · ★Token 预算控制器 · JSONL Trace
（★ = 模板没有、本项目新增）
```

> 上图是**运行时流水线视图**。分层架构（5 层 + 横切治理）、依赖方向、端口-适配器、8 条 ADR 架构决策、故障域与降级矩阵、8 条架构不变式，另见 **《架构设计.md》**。

## 3. 技术亮点

> 本节是本项目的**核心资产**。每个亮点必须同时满足两条：**技术上真难**（不是调 API）+ **能被证明**（有可展示的证据）。做不到这两条的不列入。
> 所有亮点的统一讲法只有一个主线：**把"要求模型自觉做到的事"，改成"由流水线强制执行"**。

### 3.1 亮点分层总览

| 层 | 亮点 | 技术含量来自 | 面试深挖方向 | 难度 |
|---|---|---|---|---|
| **L1 核心算法** | 引用忠实性审计 / 矛盾检测与分歧呈现 / 混合检索 + RRF + Rerank | 算法设计 + **成本约束下的近似策略** | 为什么分组批量？为什么先聚类？RRF 的 k 为什么取 60？ | ★★★ |
| **L2 编排深度** | Send 动态扇出 / interrupt 人机协同 / 断点续跑 / **状态 reducer 正确性** | LangGraph 高级特性的**真实使用**，不是 hello world | 不加 reducer 会怎样？interrupt 怎么和 checkpointer 配合？恢复时怎么不重复扣额度？ | ★★★ |
| **L3 工程治理** | 预算账户 + 分级熔断 / 模型路由 / 全链路 Trace / 离线回放 | 成本工程 + 可观测性 + 可测试性 | 熔断的不变式是什么？怎么证明记账准？怎么证明测试真的不联网？ | ★★ |
| **L4 产品设计** | 三张表（成本 / 质量 / 失败案例）/ 评测流水线 + baseline / 研究闭环准入 | 把系统当产品运营，而不是交作业 | 指标口径怎么定义？baseline 选哪几个？为什么只沉淀 supported？ | ★★ |

**取舍原则**：L1 与 L2 是技术深度的地基，**必须做扎实**——做不扎实，整个项目会退化成教程复刻；L3 性价比最高（单看每一项都不难，但组合起来是"工程师思维"的直接证据）；L4 负责把前两层翻译成面试官一眼能看懂的东西。

### 3.2 与"教程级 RAG Demo"的差异对照

同一件事有三种做法。本项目的差异全部落在"**从请求模型，变成架构强制**"这条线上。

| 能力 | 教程 / 一般做法 | 本项目做法 | 差异本质 |
|---|---|---|---|
| 检索 | 单一向量召回 top-k | BM25 + jieba + 向量 RRF 融合 + rerank + 去重 | 从"能召回"到"排得准" |
| 引用 | 在 prompt 里要求"标注来源" | 编号体系（唯一 / 可反查）+ 完整性校验 + **逐句忠实性审计** | **从"请求模型"变成"架构强制"** |
| 信源冲突 | 不处理，或让模型自己调和 | 聚类检测 + 单列"争议与分歧"章节，拒绝调和 | 把幻觉风险显式暴露出来 |
| 并行 | 固定两条分支 | Send 按子问题数量动态扇出 + reducer 保正确性 | 从"写死流程"到"按数据塑形" |
| 成本 | 无概念 | 预算账户 + 分级熔断 + 单价表 + 记账与账单对账 | 从"跑得起"到"算得清" |
| 质量 | "感觉效果不错" | 五指标 + **baseline 对照** + 人工标注校准 | 从"自评"到"可比" |
| 失败 | 不复盘 | `docs/cases/` 真实失败案例库 + 失败模式总表 | 从"没出错"到"出错了有据可查" |
| 测试 | 无 | 节点纯函数 + 依赖注入 + 离线回放 | 从"手动点点看"到"能自动验证" |

**一句话定位**：不是"我做了个 RAG"，而是"**我把 RAG 里所有不可信的地方，逐个变成了可验证的工程约束**"。

### 3.3 九项亮点逐项拆解

每项统一四问：**难在哪 → 怎么做 → 怎么证明 → 做不出来退到哪**。最后一问是"可行"的落点。

#### L1-1 · 引用忠实性审计（Citation Auditor）　★★★

- **难在哪**：①朴素做法"每句一次调用"会让调用数随报告长度线性爆炸，审计成本盖过主链路；②审计者本身也是 LLM，会误判，必须可校准而不能"信它"；③降级动作不能污染报告原文。
- **怎么做**：报告拆句 → 抽出带引用句 → **按 `citation_id` 分组** → 每组一次调用（证据原文 + 该组全部 claim）→ 逐条返回 `verdict ∈ {supported, unsupported, partial}`。flash 初筛，拿不准的交强模型复核。动作三档：`keep` / `downgrade`（标"未证实"）/ `rewrite`（章节重写，≤ 1 次）。**调用次数从"句子数"降到"引用数"**。
- **怎么证明**：注入 5 条假引用 → 全部被识别并降级；评测报告含"审计判定准确率 + 人工标注样本量"（防止自评自嗨）。
- **退到哪**：分组批量若判定质量不稳，退为"逐句 + 抽样强模型复核"，链路仍完整、仍可演示。
- **落点**：T4.1 / T4.2；数据结构 `AuditOut`（§6）。

#### L1-2 · 矛盾检测与分歧呈现　★★★

- **难在哪**：两两比对是 O(n²)，证据一多就烧穿预算；且"矛盾"的判定标准本身模糊（口径不同 ≠ 结论冲突）。
- **怎么做**：同子问题证据先做**主题 embedding 聚类**，仅在簇内两两比对，每簇 ≤ 6 对、全局 ≤ 30 对，超出按簇内相似度降序截断（上限写进配置）。输出 `conflicts[{claim_a, source_a, claim_b, source_b, topic, severity}]`。analyst 据此单列"争议与分歧"章节，**并列双方口径，不做调和**。
- **怎么证明**：构造矛盾信源 → `conflicts[]` 非空；报告出现分歧章节且双方来源可点。
- **退到哪**：聚类阈值不稳时，退为"按实体 / 指标名匹配后比对"——同样是一个讲得清的近似策略。
- **落点**：T3.7 / T3.8。

#### L1-3 · 混合检索 + RRF + Rerank　★★

- **难在哪**：中文 BM25 不分词近似失效；两路检索的分数**量纲不同、不可直接相加**，必须用秩融合。
- **怎么做**：jieba 分词建 BM25 索引（中文前置条件）+ Chroma 向量召回 → RRF `score(d) = Σ 1/(k + rank_r(d))`，k = 60 → 取 top 20–50 → qwen3.7-text-rerank 精排 top 5–10 → URL / 内容 hash 去重。
- **怎么证明**：**消融实验**——纯向量 / 纯 BM25 / 混合三组在评测集上的引用有效率对比。有这张表，这个亮点才立得住。
- **退到哪**：rerank 不可用时退为 RRF 直出，链路仍完整。
- **落点**：T3.1–T3.4。

#### L2-1 · Send 动态扇出 + 状态 reducer 正确性　★★

- **难在哪**：**这是全项目最容易静默出错的地方**。LangGraph 默认是覆盖语义，并行分支写同一个 list 字段会互相覆盖，而且**不报错、不警告**——现象是"证据莫名其妙变少了"。
- **怎么做**：Send 按 `sub_questions` 生成 N 路；`evidence` / `judgments` / `gaps` / `conflicts` / `audit_results` / `memory_hits` / `errors` 全部标注 `Annotated[list, operator.add]`；**`cost_incurred` 同样必须累加 reducer**（横切共享的预算增量，并行分支会同时记账；`fuse_level` 由它派生，不单独维护，见《架构设计.md》ADR-02）。
- **怎么证明**：**一条单测**——构造 3 路并行 Send，断言 `len(evidence) == 3` 而非 1。这条测试本身就是加分项：它证明你知道这个坑存在。
- **退到哪**：无。这是基础正确性，必须对。
- **落点**：T1.1（定义）/ T3.5（使用）。

#### L2-2 · 人机协同（interrupt / resume）+ 断点续跑　★★

- **难在哪**：interrupt 必须与 checkpointer 配套才能恢复；恢复时若识别不出"哪些检索已完成"，会**重复检索、重复扣额度**。
- **怎么做**：planner 后 `interrupt()` 抛出待确认大纲 → 用户编辑后 `Command(resume=edited_plan)` 继续，也可一键跳过；`thread_id` 关联检查点；CLI 用同步 `SqliteSaver`，FastAPI 用 `AsyncSqliteSaver`（同步 saver 在事件循环里会阻塞或报错）。
- ⚠️ **官方文档明确的两个坑（2026-09-10 补查 LangChain 官方文档）**：
  ①**resume 时整个节点从头重新执行**——原文 *"The graph resumes from the start of the node, re-executing all logic"*。因此 `interrupt()` **之前**的副作用（检索调用、写库、扣费）会**重复触发**。防护：把 interrupt 放在节点最前面，或加状态守卫（先查 `plan_approved` 再决定是否重跑副作用）。**没有这一层，"恢复时不重复检索"这条验收根本过不了。**
  ②`Command(update=...)` **不能**单独作为 invoke 输入来续跑对话（会看起来"卡住"），续跑必须用 `Command(resume=...)`；若要开启新回合则传普通 dict，才会从 `__start__` 重新开始。
- **怎么证明**：kill 进程后重启可恢复，且 trace 中**无重复的检索事件**。
- **退到哪**：分期退化——先做"可跳过确认"，再做"可编辑大纲"。
- **落点**：T5.1 / T5.4 / T5.5。

#### L3-1 · Token 预算治理 + 分级熔断　★★

- **难在哪**：预算账户是横切共享状态，在 Send 并行分支下有写竞态（同 L2-1）——架构上的解法是**把预算做成派生值而非可变状态**，只累加"花费增量"，`fuse_level` 由增量算出（详见《架构设计.md》ADR-02）；此外熔断分级如果没有不变式，很容易做成"直接把服务杀掉"。
- **怎么做**：`cost = tokens × 单价`（单价表 config 化，含真实价格）；阈值 `cost_incurred / budget_cfg.total_tokens ≥ 0.70 → L1`（轻任务切小模型 / 本地），`≥ 0.90 → L2`（停补检 + 上下文截断 + 审计只跑初筛）。**不变式：任何级别下报告都必须产出**——熔断的目的是降质保交付，不是停止服务。
- **怎么证明**：记账与平台账单误差 < 5%；预算调小后熔断触发、报告仍产出并在报告头标注降级级别。
- **退到哪**：先做 L0 / L2 两级（超限即停），再加 L1 精细档。
- **落点**：T0.5 / T4.3 / T4.4。

#### L3-2 · 全链路 Trace + 离线回放　★

- **难在哪**：Trace 的价值在于**定位慢节点**，不是打日志；离线回放要求所有外部依赖可注入——这反过来约束了架构（功能设计 D2）。
- **怎么做**：JSONL 事件 `{ts, node, event, model, tokens, cost}`，每节点 start/end 成对；Tavily 响应录制为 fixture，`SearchClient(mock=True)` 回放；前端时间线 / 成本面板从 **SSE 事件聚合**，不直接读文件。
- **怎么证明**：trace 无孤儿 start；mock 模式下全链路离线跑通、**额度零消耗**。
- **退到哪**：无。可测试性是所有其他亮点的地基。
- **落点**：T0.5 / T2.1 / T6.7。

#### L4-1 · 评测流水线（含 baseline 对照）　★★

- **难在哪**：指标口径必须**先定义后测量**，否则数字不可复现；只有"自己 vs 自己"的版本回归等于自嗨。
- **怎么做**：五指标——**每份报告 Token 成本（首位）** / 引用有效率 / 大纲覆盖度 / 完成率 / 延迟。token 与延迟是客观计量；主观指标以人工标注子集为校准基准。**加三组 baseline**：裸 LLM 直答 / 单轮 RAG / Tavily + LLM 无审计。
- **怎么证明**：`python -m eval` 输出评测报告，每项指标带"本系统 vs baseline"两列。
- **退到哪**：T3.9 的最小版（成本 + 引用有效率）已在 P3 落地，完整版做不完不影响主线。
- **落点**：T3.9 / T7.1–T7.3。

#### L4-2 · 研究闭环 + 准入控制　★★

- **难在哪**：把结论直接入库会造成**自我投毒**——错误结论变成"已有知识"，被后续调研当作前提复用，错误随时间累积且越来越难发现。
- **怎么做**：双 collection（`docs` / `research_memory`）；`MemoryItem` 携带 `audit_verdict` 与 `report_id`；**只有 `supported` 允许入库**，并便于回溯清理。scout_local 双 collection 检索。
- **怎么证明**：构造被降级结论 → 不入库；二次调研命中 research_memory 并计入 LOC 引用。
- **退到哪**：无。不加入库准入的话，**这个功能不如不做**。
- **落点**：T7.4。

| 层 | 选型 | 说明 |
|---|---|---|
| 编排 | LangGraph | Send API 动态扇出 + interrupt/Command(resume) + checkpointer（API 已核实，2026-09） |
| **接入地域** | base_url 默认锁 **华北2(北京)**：`https://dashscope.aliyuncs.com/compatible-mode/v1` | ⚠️ 百炼新用户免费额度**仅支持华北2(北京)地域实时推理调用**；配成新加坡 `dashscope-intl` 域名则免费额度不生效、直接按量扣费。base_url 可配，但默认值锁北京 |
| 强模型 | qwen3.8-max（12 / 36 元每百万 token）/ qwen3.7-max（1.65 / 4.95） | planner / judge / analyst / auditor；每日 22:00–08:00 旗舰模型有折扣；单价表进 config（T0.5） |
| 快模型 | qwen3.8-flash（0.8 / 2.7）/ qwen3.7-flash（0.3 / 1.2）+ Ollama 本地 | intent、摘要、audit 初筛（模型路由器统一调度） |
| Embedding | DashScope **text-embedding-v4**（Qwen3-Embedding 系列；1024 默认维，可选 2048…64；单行上限 8192 token；批次 10） | 长文档备选 **qwen3.7-text-embedding**（单行 128,000 token / 2560 维 / 批次 20 / 201 语种，同为 100 万 token 免费额度）——分块粒度可放宽；Ollama bge-m3 离线兜底 |
| Rerank | DashScope **qwen3.7-text-rerank**（单条 30,000 token / 请求 120,000，官方标注 recommended） | ⚠️ **两个模型的 endpoint 与请求体结构不同**：qwen3-rerank 走 `{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-api/v1/reranks`，且**单条上限仅 4,000 token、超限直接 HTTP 400 不截断**；qwen3.7-text-rerank 走 `/api/v1/services/rerank/text-rerank/text-rerank`。gte-rerank 已于 2026-05-30 下线。兜底：本地 bge-reranker-base（CPU 可跑） |
| 向量库 | **Chroma**（纯 Python，Windows/macOS/Linux 全兼容；1.x 核心已 Rust 重写） | 双 collection：docs + research_memory；统一 VectorStore 接口，可切 Milvus Standalone（Docker）或 Milvus Lite（⚠️ 仅 macOS/Linux，官方 README 原文 "Windows is not yet supported"）。**三个静默坑（v2.2 补）**：①必须显式 `embedding_function=None` 并自传 DashScope 向量——默认 embedding 函数首次调用会**静默下载约 200MB onnxruntime 模型**且无进度提示，看起来像卡死；②`PersistentClient` **不支持多进程并发**（SQLite 文件锁，多进程写会损坏），P6 FastAPI 侧必须**单例 client**，或改 `chroma run` 起服务走 HttpClient；③telemetry 默认外发 PostHog，设 `ANONYMIZED_TELEMETRY=False` 关闭 |
| 检索融合 | rank-bm25 + jieba 分词 + RRF | 中文 BM25 必须先分词；与向量召回融合后再 rerank |
| 检查点 | SqliteSaver → PostgresSaver | docker-compose.yml 预留 |
| 记忆 | SQLite 用户画像 + 偏好注入 | 跨会话复刻模板 demo |
| 网络检索 | Tavily 免费额度（1000 credits/月，无需信用卡） | include_raw_content 拿正文；查询缓存；默认全用 basic 档（1 credit/次，advanced 2 credits 不用） |
| 后端 | FastAPI + SSE | 会话/进度事件/报告接口 |
| 前端 | Vite + React + **TS** + Tailwind | 工作台 UI + Agent 执行时间线 + 成本面板 |

> ⚠️ **单价表是二维的，不是一维的（2026-09-10 补查后修正）**：百炼采用**阶梯定价**，且按**上下文长度分档**——例：qwen3.8-max 在 0–32K 档约 12/36 元每百万 token，在 128K–256K 档约 **15/60**（输入/输出，仍是社区文章汇总值，须在控制台价格页核对）。**单一单价的 `config.PRICING` 会把成本算错，FR-20 的"记账与账单误差 < 5%"直接达不成。** 设计上 `PRICING` 必须是 `模型 × 上下文档位 → (输入价, 输出价)`。
> ⚠️ **Batch 调用虽然便宜（约 5 折），但不抵扣免费额度**——依赖免费额度开发时不可用 Batch。

## 6. 关键数据结构

```python
Plan:      { objective, sub_questions[], outlines[{section_title, description, key_points}] }
Evidence:  { source_id: "WEB1-1-1"|"LOC1-1-1", source_type, title, url, snippet, raw_content }
JudgeOut:  { summary, confidence, missing_gaps[], conflicts[{claim_a, source_a, claim_b, source_b, topic}] }
AuditOut:  { claim, citation_id, verdict: supported|unsupported|partial, action: keep|downgrade|rewrite }
BudgetCfg: { total_tokens, fuse_l1: 0.70, fuse_l2: 0.90 }              # 静态配置，不参与并发写
CostState: { cost_incurred: Annotated[float, operator.add], model_tier }  # 唯一被并行写入的预算字段
fuse_level = f(cost_incurred, BudgetCfg)                              # ★ 派生值，不是可变状态（架构设计 ADR-02）
MemoryItem:{ report_id, claim, evidence_ids[], audit_verdict: supported|unsupported|partial, created_at }  # 只有 supported 才允许写入 research_memory，防自我投毒
```

| 风险 | 对策 |
|---|---|
| 复杂度膨胀烂尾 | 每期结束跑全链路冒烟 + git tag；P5 为求职可交付线 |
| Auditor 烧 token | 只审带引用的结论句；flash 模型初筛 + 强模型复核 |
| **Auditor 判定本身会误判**（审计者也是 LLM） | 评测集预留部分题目人工标注，定期校准 auditor 判定准确率并写入评测报告 |
| Tavily 1000 credits/月（basic 1 credit/次，仅够 30-80 次全链路） | 查询缓存落盘；单次调研 6-12 查询可控；演示前预热缓存；评测用小预算模式 |
| 百炼免费额度 90 天过期、用完自动扣费 | 控制台开启"免费额度用完即停"；预算账户记账双保险；轻任务自动切 Ollama |
| 百炼限速 | 指数退避；轻任务自动切 Ollama |
| **评测"自己给自己打分"**（指标由 LLM 判定） | 五指标中 token/延迟为客观计量；引用有效率等主观指标以人工标注子集为校准基准 |
| **切换 embedding 模型导致向量空间错乱** | collection 元数据记录 embedder 标识+维度；换模型即全量重建索引，禁止混用 |
| **async 环境误用同步 checkpointer** | CLI 用同步 SqliteSaver；FastAPI 用 AsyncSqliteSaver（aiosqlite） |
| reflect + audit 叠加超时 | 预算熔断兜底，Trace 定位慢节点 |
| **免费额度地域限制**（v2.2 新增） | base_url 默认锁华北2(北京)；配置校验：若非北京域名且处于"依赖免费额度"模式，启动即告警 |
| **Chroma 默认 embedding 静默下载 200MB / 多进程并发损坏**（v2.2 新增） | 显式 `embedding_function=None` 自传向量（本来就是用 DashScope 向量）；FastAPI 侧单例 client；`ANONYMIZED_TELEMETRY=False` |
| **Tavily 额度瓶颈在开发调试期而非演示期**（v2.2 新增） | 录制/回放：真实响应落盘 fixture，开发与评测默认 mock，仅验收打真实；单次调研 6–12 查询可控 |
| **百炼 LLM 额度按"次"算只够个位数**（v2.4 新增；2026-09-10 补查修正） | 官方帮助文档：每模型 100 万 token / 90 天。按单份报告 30 万 token（估算）计 → **单模型约 3 次**。⚠️ **额度不互通、不能跨模型合并**（不同模型与快照版本各自独立），所以**不能按"系列合计十几次"估算**；且**某模型额度用完后系统不会自动切到其他模型**，必须由我们的路由器主动改 `model` 参数。对策：开发期 **100% 走离线 mock**（T2.1 录制回放），真实调用只用于录 fixture 与验收；控制台开"用完即停"（需完成实名认证）。**这是比 Tavily 更紧的约束，不要按"90 天很长"来估算** |
| **Rerank 单条 4000 token 上限触发 HTTP 400**（v2.2 新增） | 主选 qwen3.7-text-rerank（单条 30k）；若用 qwen3-rerank，必须在入库前保证 chunk ≤ 4000 token——该 API 超限**不截断、直接报错** |
| **研究闭环自我投毒**（v2.2 新增） | research_memory 只写入 audit_verdict=supported 的结论，并记录来源 report_id 便于回溯清理 |
| **Auditor 逐句核验导致调用爆炸**（v2.2 新增） | 按 citation_id 分组批量核验（同一引用的多个 claim 合并为一次调用），预计降调用次数 5–10 倍；再叠 flash 初筛 + 强模型复核 |

| 引用审计 | 注入 1 条假引用跑一遍 | 该句被标注"未证实" |
| 矛盾检测 | 用构造好的矛盾信源提问 | 报告出现"争议与分歧"章节 |
| 动态扇出 | 提一个含 5 个子问题的问题 | 时间线出现 5 路并行检索 |
| 人机协同 | 在确认点改掉一个大纲章节 | 报告结构随之改变 |
| 断点续跑 | 跑一半 kill 进程再重启 | 从断点继续，无重复检索 |
| 预算熔断 | 把预算调小 | 报告仍产出且标注降级级别 |
| 评测 + baseline | 一条命令 | 输出两列对照表 |

### 9.5 开工前自检（按此顺序执行）

1. 跑 **P-1 环境预检** → 全部 import 通过才继续；不通过先解决环境，不要边写边赌
2. 按 §8 建目录骨架 + `tests/`，**先写 T1.1 那条 reducer 单测（先红后绿）**
3. 写最小节点让图能跑通（不接真实检索），先让"状态不丢数据"这件事成立
4. 再接 LLM 网关与记账，跑完 T0.5 验收
5. 之后进入 P1

**原则**：先让"骨架 + 正确性"成立，再往外长功能。反过来做，后面每加一个功能都会带着前面的错误一起放大。

## 10. 工程规范与作品集分发

> 本项目是求职作品集，**"代码在哪、怎么看"和"代码写了什么"同等重要**。本节补上前几版遗漏的分发环节。

### 10.1 版本控制与仓库

| 项 | 约定 |
|---|---|
| 仓库 | GitHub **公开**仓库——作品集靠它分发，面试官最先看的是它 |

### 10.2 提交历史（面试官真的会看）

- **禁止最后一次性 push 全部代码**——那是最明显的"临时拼凑"信号。
- 每完成一个任务提交一次；message 用 `feat: / fix: / test: / docs:` 前缀 + 一句话说清意图。
- 每期结束打 tag（`p0`…`p6`、`v1.0`），tag 点即"当时确实跑通的版本"。
- **提交分布本身就是"我真的持续在做"的证据**，这是唯一无法伪造的材料。

### 10.3 关键文件的创建时点

### 10.4 命名与口径一致性（防止再次出现"三处三种说法"）

前几版确实出现过同一概念在三个文档三种写法（预算字段、网关文件名、模型路由归属）。约定：
