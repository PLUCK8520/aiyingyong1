# 案例 #14 · 判别编号丢方括号：一切查询退化成"拒编页"

- **标签**：P0 / 引用编号契约 / 字符串精确匹配
- **发现**：2026-09-13 真实档端到端（glm-4-flash + 离线检索，thread `kb-e2e-1`）
- **状态**：已修复（`retrieval/citations.py::normalize_citation_id`）

## 现象

用户上传自己的文档后跑调研，界面产出的是措辞得体的「证据不足，故拒编」页。
一切都**看起来符合设计**——拒编页本身就是 T7.10 为"零造假"做的正确行为，
所以第一眼根本不会怀疑是 bug。

## 根因

判别器（`evidence_judge`）回填 `citation_id` 时**丢了方括号**，写成 `LOC1-1-1`；
而证据实体里的编号是 `[LOC1-1-1]`。下游 `analyst.assess_evidence` 做的是**字符串精确匹配**：

```python
relevance.get(e.citation_id, 0)   # 键是 [LOC1-1-1]，模型给的是 LOC1-1-1 → 恒取不到
```

于是判别器明明判了 `relevance=5`，评分却挂到一个不存在的键上，`selected` 恒为空，
最后落到拒编分支。

**实测数字**：`judgments` 56 条、`evidence` 72 条，**编号交集 0**；把方括号去掉后交集 **56/56**。

## 怎么发现的

拒编页本身无懈可击，是靠追 trace 里的判别记录 + 证据编号**逐条对交集**才定位的。
关键动作是"不信任拒编页的叙事"，去查判别器到底给没给分。

## 修复

- `normalize_citation_id()`：把编号收敛成规范形态 `[KIND{轮}-{子}-{序}]` 的**唯一入口**；
- 三层兜底：schema 层 `field_validator`（挡新输出）+ 消费层 `analyst` / `evidence_judge`（兜旧 checkpoint 里的脏数据）；
- 新增回归用例 `tests/test_citations.py`、`tests/test_t710_evidence_gate.py`。

## 教训

1. **最危险的是"失败被伪装成正确行为"**。拒编页本身符合零造假叙事，让一个 P0 缺陷
   穿着"设计如此"的外衣存活。排查时永远要问：*这个"正确结果"真的是按预期路径来的吗？*
2. **跨模块的字符串契约必须单点收敛**。编号这种"一边生成、一边消费"的字符串，
   生成方与消费方各自 normalize 一定会漂移；只在一个入口做规范化，其余全走它。
