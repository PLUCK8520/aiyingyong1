## 1. 需求的两条来源

这个项目的需求来自两条轨道，混在一起会导致排期错乱，必须先分开：

| 轨道 | 需求方 | 关心什么 | 验收方式 |
|---|---|---|---|
| **A · 真实用户轨** | 需要做行业调研、但信不过 LLM 直答结论的人 | 结论能否溯源、信源冲突怎么处理、报告能不能直接用 | 拿真实问题跑，人工判断报告可用性 |
| **B · 展示轨** | 面试官 / 评审者 | 有没有工程判断力、能不能量化、是不是本人做的 | 看评测数据、案例库、代码与 demo |

**冲突时的裁决规则**：两条轨的需求都要满足；当两个实现方案都能满足 A 轨需求时，**选那个可被量化、可被展示的方案**。

这条规则的含义要说透：本项目不以"功能齐全"为目标，而以"**每条能力都有证据**"为目标。A 轨保证项目像产品而不是玩具，B 轨保证它能换来 offer。

## 2. 问题定义

### 2.1 通用 LLM 直答的四个硬伤

原方案只写了前三条，P4 是本项目的差异化重点（成本工程），必须显式立为需求。

| # | 硬伤 | **可观察的失败现象**（怎么判定复现了） |
|---|---|---|
| P1 | 结论不可溯源 | 报告中的数字或论断点不出处；或给出的链接与论断内容无关 |
| P2 | 复杂问题不会拆解 | 多约束问题只答一部分（要求"按市场规模/竞品/收费三部分输出"却只答两部分，且不自知） |
| P3 | 多源不会综合 | 信源打架时，要么并置不提、要么强行调和成一个并不存在的"综合结论" |
| P4 | 成本不可控 | 单次深度调研的 token 消耗无法预估；链路跑飞后无法叫停，钱白烧 |

### 2.2 替代方案对比（为什么必须做流水线）

| 替代方案 | P1 | P2 | P3 | P4 | 结论 |
|---|---|---|---|---|---|
| 通用 LLM 直答 | ✗ | ✗ | ✗ | ✗ | 全中四害 |
| 单轮 RAG（检索 + 直答） | 部分解决 | ✗ | ✗ | ✗ | 只治了一半 P1 |
| 现成深度研究产品 | ✓ | ✓ | 部分 | ✗ | 无法定制、过程不可展示、无法量化 |
| **Attest 多节点流水线** | ✓ | ✓ | ✓ | ✓ | 需同时具备审计节点与预算治理 |

**由 P1-P4 反推出的四条必备能力**：引用可核验、任务可拆解、冲突可呈现、成本可治理。这四条是本项目存在的理由，任何新增功能若不能强化这四条中的至少一条，应被拒绝（见 §6）。

## 3. 用户角色

| 角色 | 描述 | 主要诉求 |
|---|---|---|
| **R1 调研发起者** | 给出调研问题，需要一份能直接拿去用的报告 | 快、可溯源、冲突讲清楚、别烧钱 |
| **R2 报告复核者** | 拿到报告后逐条验证引用 | 能点开原文；能识别哪些结论是"未证实"的 |
| **R3 评审者** | 面试官 / 答辩老师，5 分钟内判断技术深度 | 可量化证据、失败案例、能自己跑一遍 |

R3 不是"虚构用户"——本项目的验收场景里他会真实出现，且是最终裁决人。这不是妥协，是诚实。

## 4. 用户故事

每条附**验收口径**，写不出验收口径的故事不予保留。

| 编号 | 角色 | 我希望…… | 验收口径 |
|---|---|---|---|
| US-01 | R1 | 简单问题秒回，不要什么都走完整流水线 | "你好"类输入 ≤ 3s 返回，且不触发任何检索调用 |
| US-02 | R1 | 开跑前看到大纲并修改它 | 可增删章节、改标题，resume 后按新大纲执行 |
| US-03 | R1 | 实时知道跑到哪了、花了多少 | 界面显示当前节点、已完成节点、累计 token 与成本 |
| US-04 | R1 | 每句带引用的话都能点开看原文 | 点击引用编号弹出证据原文片段 |
| US-05 | R1 | 信源冲突时如实呈现而非替我调和 | 构造矛盾信源 → 报告出现"争议与分歧"章节且双方口径并列 |
| US-06 | R2 | 知道哪些结论没被证实 | 审计未通过的句子被标注/降级，不静默保留 |
| US-07 | R1 | 预算超了不要白跑，拿到已有结果 | 预算调小后报告仍产出，并标注降级级别 |
| US-08 | R1 | 中断后能继续跑 | 进程强杀后重启，从检查点恢复且不重复已完成的检索 |
| US-09 | R1 | 二次问相关问题能更快 | research_memory 命中，命中项进入 LOC 引用 |
| US-10 | R3 | 5 分钟看到成本与质量的量化证据 | 一条命令输出含 baseline 对照的评测表 |

## 6. 非功能需求（NFR）

学生项目最容易在这块失守——只写功能不写约束，导致"能跑但不可用"。

| 编号 | 需求 | 目标值 | 实测状态 |
|---|---|---|---|
| NFR-01 | **单份报告成本** | ≤ 30 万 token / 份（含审计与 ≤ 2 轮补检）；**该值为估算，P3 尺子出真值后回填** | 待测 |
| NFR-02 | **延迟** | direct ≤ 3s；research 全链路 ≤ 5 min（可中断、可续跑） | 待测 |
| NFR-03 | **降级不停机** | 预算耗尽 / 模型限流 / 检索失败时报告仍能产出，并标注降级级别 | 待验证 |
| NFR-04 | **可观测** | 任一节点的耗时与 token 可事后追查，不依赖复现 | — |
| NFR-05 | **可复现** | 默认离线 mock 可跑通全链路；评测固定 seed | — |
| NFR-06 | **可移植** | Windows + Python 3.13 单机可跑，不依赖 Docker | P-1 验证 |
| NFR-07 | **密钥安全** | API Key 只从环境变量读，禁止入日志、入 trace、入 git | — |
| NFR-08 | **额度安全** | 免费额度耗尽即停；不做静默扣费 | 控制台配置 |
| NFR-09 | **可测试性** | 节点应为纯函数（`node(state) -> dict`，返回状态增量、不构造外部客户端）；外部依赖（LLM / Tavily / Rerank / 向量库）全部可注入可 mock | — |
| NFR-10 | **引用可核验率** | 报告中可点击引用占全部引用的 100% | — |
| NFR-11 | **索引一致性** | 切换 embedding 模型必须全量重建，禁止混用向量空间 | — |

> NFR-01 / NFR-02 填的是**目标值（估算）**，不是实测值——表中已标注"待测"。**不要把它们当成已知结论引用**：P3 出尺子后必须用真值替换，否则"成本工程"这条叙事没有落点。

## 7. 明确不做（Out of Scope）

写清"不做"和写清"做"同样重要——它是防止项目膨胀的唯一闸门。

| 不做 | 原因 | 例外条件 |
|---|---|---|
| 多用户 / 鉴权 / 配额 | 单机单用户作品集，做了也没人用，成本高 | 若后续要上线 demo 再议 |
| 真实分布式部署（实切 Postgres / Milvus） | 属于"简历可写但没跑过"的虚项，深挖会露怯 | 若时间有富余可做压测留档 |
| 自建爬虫与反爬对抗 | 法律与工程量双高，Tavily 已覆盖 | — |
| 模型微调 / 自训 judge | 无数据无算力，且偏离应用层定位 | 远期（《审查报告-2026-09-08.md》C 节发展方向第 5 条） |
| 移动端 / 小程序 | 与核心叙事无关 | — |
| **追问模式**（T7.5） | 复用 thread 证据的收益低于其复杂度，原方案已标可砍 | 待用户确认 |
| **图表生成**（T7.6） | 是钩子不是功能，做了也不算差异化 | 待用户确认 |
| 多模态（图片/视频输入） | 与"可溯源调研"主线无关 | — |

## 8. 优先级与裁剪线

| 档位 | 范围 | 含义 |
|---|---|---|
| **P0** | FR-01 ~ FR-07、FR-09 ~ FR-19、FR-20 ~ FR-21、FR-23 ~ FR-24、FR-27 ~ FR-30（共 26 条） | **缺任何一条，项目不成立**。P5 结束前必须全绿 |
| **P1** | FR-08 检索去重、FR-22 模型路由、FR-25 用户画像、FR-26 研究闭环、FR-31 完整评测 | 求职展示的差异化，**P7 结束前补齐**（其中 FR-22 随 T4.4 落在 P4、FR-25 随 P5 落地） |
| **P2** | FR-32 报告导出；以及已建议砍掉的 T7.5 追问模式 / T7.6 图表生成 | 时间够才做，砍掉不影响主线 |

**v2.4 调整说明**：FR-07（动态并行）、FR-12（矛盾检测）、FR-19（审计质量验证）、FR-29（执行可视化）由 P1 提升为 **P0**。原因：这四条在《方案》§3 里被列为 ★★ / ★★★ 级核心亮点，若在需求里只标"应该有"，就会出现**"方案当核心、需求当可选"的双标准**——面试官追问优先级时会自相矛盾。约定：**方案里当亮点的，需求里必须是 P0。**

**三条裁剪线**：

1. **P2 结束**：单轮可溯源报告可用 → 能演示但讲不深
2. **P5 结束**：P0 需求全绿 + 人工确认与续跑 → **完整可讲的版本**
3. **P6 结束**：Web 工作台 + 时间线 → **可投递展示的版本**

超过 P6 仍要继续加功能时，必须走"可选插件"路线，不得改动核心链路（呼应方案 §5）。
